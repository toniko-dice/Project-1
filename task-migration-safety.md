# Задача: миграциите да не могат да губят данни

Причина: миграцията `20260901_142626_product_drafts` изтри всички връзки
към продукти от другите таблици. Началната страница остана без продукти.

---

## Какво точно се обърка

В `up()` на миграцията:

```
позиция 25154:  PRAGMA foreign_keys=OFF
позиция 25838:  PRAGMA foreign_keys=ON       ← върнато твърде рано
позиция 42859:  DROP TABLE `products`        ← с ВКЛЮЧЕНИ външни ключове
```

Таблиците `pages_rels`, `_pages_v_rels`, `header_rels`, `menu_panels_rels`
и всички други `*_rels` сочат към `products(id)` с `ON DELETE CASCADE`.
При `DROP TABLE products` с включени ключове SQLite изтрива всеки ред,
който сочи натам. Продуктите оцеляха (копирани в `__new_products`), но
връзките към тях — не.

Генераторът на Payload прави `OFF → пресъздаване → ON` за всяка таблица
поотделно. При ръчно дописване редът се е разместил.

**Това не е упрек — е причината да съществува тази задача.** Ръчното
дописване на миграции ще се случва пак. Трябва предпазни мерки, които
работят и когато някой сгреши.

---

## 1. Възстановяване на връзките на началната страница

Провери дали има архив отпреди миграцията (Настройки → Архиви, или
папката `backups/`). Ако има:

- извади от архивната база **само** редовете на `pages_rels` и
  `_pages_v_rels`, които сочат към `products`
- вмъкни ги в текущата база, ако номерата на продуктите съвпадат
  (провери — при миграцията номерата се запазват, но потвърди)
- изпиши колко реда си върнал

Ако няма архив — кажи, и собственикът ще избере продуктите наново от
админа. Не измисляй кои продукти къде са били.

Провери и другите `*_rels` таблици за загуби: `header_rels`,
`menu_panels_rels`, `products_rels` (свързани продукти, сравнителни
таблици). Изпиши по таблица: редове преди (от архива) и сега.

---

## 2. Поправи самата миграция

В `20260901_142626_product_drafts.ts`, и `up()` и `down()`:

- `PRAGMA foreign_keys=OFF` **като първи ред**
- `PRAGMA foreign_keys=ON` **като последен ред**
- нищо между тях не пипа ключовете

Миграцията вече е изпълнена, така че поправката няма да върне
изгубеното. Но `down()` ще се изпълни, ако някой я връща назад — и ще
направи същата беля. А и служи за образец на следващите.

---

## 3. Архив преди всяка миграция — автоматично

В `package.json`:

```json
"migrate": "payload run src/pre-migrate.ts && payload migrate"
```

`src/pre-migrate.ts`:
- прави архив през съществуващия `createBackup` от `src/lib/backup.ts`
- с `includeMedia: false` — бърз, само базата
- име: `Автоматично преди миграция <дата час>`
- **`protected: true`** — да не бъде изтрит от автоматичното чистене
- ако архивът се провали → **спира с грешка и миграцията не се пуска**

Така „забравих да направя архив" става невъзможно.

---

## 4. Проверка на здравето — преди и след

`src/health-check.ts`, пуска се с `npm run health`:

Брои и изписва:
- продукти, категории, страници, медия — общо и публикувани
- за всяка `*_rels` таблица: брой редове по целева колекция
  (`pages_rels → products: 11`, `header_rels → menu-panels: 8` ...)
- начална страница: продуктови блокове и продукти във всеки
- продукти без основна снимка
- медия без нито един файл на диска

Записва резултата в `.health/<дата час>.json`.

**При второ пускане сравнява с предишния** и изписва разликите:
```
⚠ pages_rels → products: 11 → 0   (−11)
  products: 16 → 17   (+1)
```

Разлика с минус на `*_rels` е сигнал за точно тази беля.

В `package.json`:
```json
"migrate": "payload run src/pre-migrate.ts && payload run src/health-check.ts && payload migrate && payload run src/health-check.ts"
```

Тоест: архив → снимка на състоянието → миграция → снимка → разлика.
Ако миграцията изяде връзки, ще пише в терминала веднага, а не когато
собственикът отвори сайта.

## 5. Правило в CLAUDE.md

Добави в раздела „Решения, които НЕ бива да се връщат назад":

```
### 6. Миграции, които пресъздават таблици

SQLite не може да променя колони — Payload прави нова таблица, копира
редовете и изтрива старата. Ако в момента на `DROP TABLE` външните
ключове са включени, всички връзки към тази таблица от другите таблици
се изтриват (ON DELETE CASCADE).

Миграцията 20260901_142626 направи точно това с `products` и началната
страница остана без продукти.

Правила:
- `PRAGMA foreign_keys=OFF` е ПЪРВИЯТ ред на up() и down(),
  `=ON` е ПОСЛЕДНИЯТ. Нищо помежду.
- `npm run migrate` прави архив и проверка преди и след. Не го
  заобикаляй с `payload migrate` директно.
- След включване на чернови на колекция със съществуващи записи всеки
  от тях трябва да мине през запис — иначе е невидим в админа.
```

---

## Правила за изпълнение

- Никакви нови зависимости — `sqlite` достъпът е през `payload.db`
  както в `backup.ts`
- Не пускай `migrate:fresh`. Никога.
- Не изтривай нищо — тази задача само добавя и възстановява
- Не пипай съдържанието на началната страница освен връзките към
  продукти, и то само от архив

---

## Как да разбереш, че е готово

- `npm run health` изписва таблица с бройки; второ пускане изписва
  „без промени"
- `npm run migrate` без нови миграции: прави архив, проверява два пъти,
  казва „нищо за изпълнение"
- В Настройки → Архиви има архив „Автоматично преди миграция", отбелязан
  като защитен
- Началната страница показва продуктите в четирите блока — от архив
  или след ръчен избор
- В `20260901_142626_product_drafts.ts` първият ред на `up()` и
  `down()` е `foreign_keys=OFF`, последният — `=ON`
- CLAUDE.md има точка 6
