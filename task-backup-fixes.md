# Задача: поправки по архивирането

Отнася се за `src/lib/backup.ts`, `src/restore-on-boot.ts` и
`src/collections/Backups.ts`.

Механизмът работи и е добре построен. Тези три поправки закриват единствения
сценарий, при който може да се загубят данни, и слагат таван на диска.

**Не преправяй нищо друго в тези файлове.** `VACUUM INTO`, двустъпковото
възстановяване и предпазният архив преди възстановяване са правилни решения
и остават както са.

---

## 1. Не трий преди да си копирал

**Проблемът.** В `src/restore-on-boot.ts` редът в момента е:

```
rm ecoflow.db (+ журналните файлове)   →   copyFile от подготвената папка
rm media/ (цялата)                     →   cp от подготвената папка
```

Ако копирането се провали по средата — пълен диск, липсващи права,
прекъснато захранване — оригиналът вече е изтрит и на негово място стои
нищо или половин файл.

**Как да стане.** Първо се копира настрани, после се разменят имената.
Преименуването в рамките на един диск е моментално и не може да остави
нещата наполовина.

### За базата
```
1. copyFile  .restore-staging/ecoflow.db  →  ecoflow.db.incoming
2. Провери incoming (виж точка 2). При проблем: изтрий incoming, спри,
   НЕ пипай живата база.
3. Премести журналните файлове (-journal, -wal, -shm) в
   ecoflow.db.pre-restore-* — не ги изтривай
4. rename  ecoflow.db          →  ecoflow.db.pre-restore
5. rename  ecoflow.db.incoming →  ecoflow.db
6. Ако стъпка 5 се провали: rename обратно pre-restore → ecoflow.db
   и спри с ясно съобщение
7. При успех остави pre-restore файловете на място. Трият се при
   следващото успешно пускане, не веднага
```

### За снимките
```
1. cp  .restore-staging/media  →  media.incoming
2. Провери, че media.incoming съществува и има поне толкова файлове,
   колкото пише в arhiv.json. По-малко = непълно разархивиране, спри
3. rename  media          →  media.pre-restore
4. rename  media.incoming →  media
5. При провал на 4: rename обратно
6. При успех изтрий media.pre-restore
```

**Правило:** живият файл се маха само след като заместникът е на диска
и е проверен.

## 2. Проверявай, че архивът е истински

**Проблемът.** В момента се проверява само че `ecoflow.db` съществува в
разархивираното. Файл с нулева дължина минава проверката и се слага на
мястото на работещата база.

**Как да стане.** Преди подмяна се проверява:

1. **Размер по-голям от нула.** Празен файл се отхвърля веднага.
2. **Заглавие на файла.** Всяка SQLite база започва с шестнайсет байта
   `SQLite format 3\0`. Прочети ги и ги сравни.
3. **Наличие на `arhiv.json`** в разархивираната папка — ако липсва,
   архивът не е правен от този механизъм.

Проверката се прави на две места:
- в `stageRestore` — за да се хване веднага при натискане на бутона,
  докато потребителят гледа
- в `restore-on-boot` — преди подмяната, защото между двете може да е
  минало време

При провал: не се пипа нищо, папката `.restore-staging` се запазва,
съобщението казва конкретно кое е сбъркано.

## 3. Архиви, които не се трият

**Проблемът.** `pruneOldBackups` пази последните по дата и трие
останалите. Това означава, че предпазният архив отпреди възстановяване
може да изчезне, ако след него се направят достатъчно други.

**Как да стане.**

Ново поле в колекция `Backups`:
```
name: 'protected'
type: 'checkbox'
label: 'Не изтривай автоматично'
defaultValue: false
admin: { description: 'Отбележете архивите, които искате да останат завинаги.' }
```

- `pruneOldBackups` пропуска отбелязаните — те не се броят към лимита
- Архивите, създадени автоматично преди възстановяване, се записват
  с `protected: true`
- В списъка колоната се вижда, за да личи кои са защитени

## 4. Таван на диска

**Смени `KEEP_LAST` от 10 на 4** в `src/lib/backup.ts`.

При 400-800 продуктови снимки всеки пълен архив ще е стотици мегабайти.
Четири е достатъчно за връщане назад при грешка, без да се трупат гигабайти.

Защитените архиви (точка 3) са извън тази бройка — колкото и да отбележиш,
те остават.

Освен това:
- Добави в описанието на колекцията общия размер на всички архиви,
  за да се вижда без броене
- Ако общият размер надхвърли **5 GB**, покажи предупреждение над списъка

---

## 5. Дневният архив без снимки

Задачата по график в `src/jobs/backupTask.ts` прави пълен архив със
снимки всяка нощ. Базата се променя всеки ден, снимките — рядко.

Промени я на:
- **всяка нощ** — само базата (`includeMedia: false`), име
  „Автоматичен архив (само база)"
- **в неделя** — пълен, със снимките

Така десетте архива тежат много по-малко, а базата пак е покрита всеки ден.

Ако Payload не позволява два различни графика за една задача, направи
две задачи.

## 6. Правила

**Не пипай:**
- `VACUUM INTO` — правилният начин за снимка на работеща SQLite база
- двустъпковото възстановяване през маркер и рестарт — заради заключения
  файл на Windows
- предпазния архив преди възстановяване
- `access` правилата на колекцията
- нищо извън трите файла, изброени най-горе

**Никакви нови зависимости.** Всичко се прави с `fs/promises`.

**След промените:**
```
npm run generate:types
npm run migrate:create
```
Прегледай миграцията, преди да я пуснеш.

---

## 7. Как да разбереш, че е готово

- Възстановяване от валиден архив минава и базата се подменя
- След успешно възстановяване съществува `ecoflow.db.pre-restore`
- Архив с изкуствено повреден `ecoflow.db` (нулева дължина) се отхвърля
  **и живата база остава непокътната**
- Архив без `arhiv.json` се отхвърля
- Пазят се последните четири незащитени архива; петият по ред изтрива
  най-стария
- Отбелязан като защитен архив не се трие, дори когато има повече от
  четири по-нови
- Автоматичният архив отпреди възстановяване се появява отбелязан
- Над списъка се вижда общият размер на архивите
- Нощната задача прави архив само с базата; неделната — със снимките

**Провери третата точка наистина.** Направи архив, отвори zip-а, замени
`ecoflow.db` с празен файл, качи го и пробвай възстановяване. Живата база
трябва да оцелее. Това е целият смисъл на задачата.
